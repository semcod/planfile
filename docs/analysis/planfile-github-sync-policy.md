# Analiza: Main store GitHub synchronization architecture and campaign opt-in policy

<!-- docs:section question -->
## Question

Should the Planfile main store execute an unbounded scheduled incremental synchronization to GitHub Issues, or maintain campaign-scoped opt-in for outbound tracker mirroring?

<!-- docs:section scope -->
## Scope

The primary Planfile store for `semcod/planfile`, the GitHub integration backend (`planfile.sync.github`, `planfile.sync.incremental`, `planfile.sync.retry`), state tracking in `.planfile/sync/github.state.yaml`, and outbound delivery boundaries for tickets created via CLI and API.

<!-- docs:section method -->
## Method

Analysis of live backlog volume (217 open tickets vs 9 remote GitHub issues), empirical examination of recent campaign issues (#328 PLF-21690, #329 PLF-21654), verification of rate limit boundaries in the GitHub API, and audit of `planfile/sync/incremental.py` filtering contracts.

<!-- docs:section evidence -->
## Evidence

1. Backlog audit: The live Planfile store holds over 200 open tickets, largely generated by autonomous agents, internal diagnostic probes, and local triage cycles.
2. Rate-limiting invariants: Unbounded batch creation of 200+ issues violates GitHub secondary rate limits (triggering HTTP 403 / 429 and token abuse throttling).
3. Existing successful publications: Issues #328 and #329 were created with deduplication markers (`<!-- planfile:deduplication-key=... -->`) under explicit campaign execution without noise.
4. Incremental delivery contract: `planfile.sync.incremental.sync_incremental` strictly enforces `if ticket is None or 'github' not in (ticket.integration or []): continue`.

<!-- docs:section facts -->
## Facts

1. The Planfile CLI and sync subsystem already provide idempotent incremental delivery via `planfile sync github --direction to --incremental --max-tickets N`.
2. Outbound issue creation records mapping entries in `.planfile/sync/github.state.yaml` (`ticket_map`).
3. Blanket scheduled export of all local tickets without qualification would flood GitHub with transient internal records.
4. Existing production services (e.g. `c2004-planfile-autosync.service`) already enforce explicit opt-in filtering (`github-auto-sync` label / scope) for safe unattended operation.

<!-- docs:section hypotheses -->
## Hypotheses

Retaining campaign-scoped opt-in and explicit integration targeting for outbound GitHub synchronization preserves tracker signal-to-noise ratio, prevents API quota exhaustion, and satisfies idempotency guarantees through the existing `ticket_map` and deduplication keys.

<!-- docs:section limitations -->
## Limitations

Tickets created without `integration: ["github"]` or an explicit campaign marker remain local to the Planfile store until opted in or published via an authorized campaign.

<!-- docs:section recommendations -->
## Recommendations

1. Policy Decision: Outbound issue creation from the main store remains **campaign-scoped and explicit opt-in**. Tickets must carry `integration: ["github"]` or an authorized campaign deduplication key to be mirrored to GitHub.
2. Idempotency Invariant: All outbound synchronizers must resume from `.planfile/sync/github.state.yaml`'s `ticket_map` and check existing deduplication markers before issuing POST requests.
3. Bounded Delivery: Automated synchronization runners must restrict batch size (`--max-tickets 2`) and respect persisted retry cooldowns.
